# 011. Прореженный спектр отдельным артефактом

> **ОТЛОЖЕНО. Не реализуется сейчас.** Система строится на PNG
> (решение [002](002-pixel-only.md) остаётся в силе). Артефакт — проработанное
> направление развития: формат, требования к содержимому и обоснование готовы,
> так что при необходимости это берётся и делается без повторного разбора.
>
> **Что должно произойти, чтобы вернуться к этому решению:**
> - измеренный RMS извлечения по пикселям окажется недостаточным
>   (порог фазы 0 — 0.5 кГц), особенно на полосе 240 кГц, где пиксель даёт 400 Гц;
> - или правка вёрстки водопада в клиенте начнёт регулярно ломать извлечение;
> - или понадобится точность выше пиксельной по другой причине.
>
> Формат и требования к содержимому целиком описаны ниже, в `algorithms.md`
> их нет — там действующий пиксельный путь.

## Что изменилось в постановке

При принятии 002 действовало ограничение «клиент и сеть не трогаем», и главным
доводом было «работает на всей истории наблюдений». Ограничение снято,
а довод оказался неверным.

### Измерения

**`satnogs:wf-dat` пишет только клиент 2.2.x, появившийся около июля 2026.**

| Период | С метаданными | Версии клиента |
|---|---|---|
| 2024-07 | 0 / 6 | 1.2.2 |
| 2025-07 | 0 / 6 | 1.2.8 |
| 2026-03 | 0 / 6 | 1.2.8, 2.1.0 |
| 2026-07-01 | 0 / 8 | 2.1.0, 1.2.8, 2.0.0 |
| 2026-07-20 | 6 / 8 | 2.2.0, 2.2.2 |

То есть «вся история» — это около месяца.

**Парк смешанный.** На 67 свежих наблюдениях: `2.2.2` — 57, `2.2.0` — 5,
`2.1.0` — 3, `1.2.8` — 2. Метаданные есть у 62 из 67 (93%), 7% продолжают
приходить без них. Прошлая раскатка шла с июля по август и не завершилась.

**Полосы:** 57600 — 54, 48000 — 7, 240000 — 1. В пикселях это 96, 80
и **400 Гц/пиксель** — последняя цифра уже сопоставима с RMS фита.

**Запасного пути нет:** `satnogs_rx_samp_rate` станции через API не отдаётся,
поэтому полоса для наблюдений без метаданных невосстановима в принципе.

**Калибровка по делениям оси перестала быть страховкой на будущее.** Она была
нужна прямо сейчас всему парку: у наблюдений 2.2.x есть `wf-dat`, но нет
`tabs[0]`, а это ~56 Гц систематики на каждом наблюдении.

## Проработанное предложение

Клиент выгружает прореженный спектр отдельным артефактом.

### Формат

Порядок байт little-endian.

```
magic    b"SOWF"          4 байта
version  uint16           = 1
hdr_len  uint32
header   JSON utf-8, hdr_len байт
data     n_rows × (tabs_us int64, spec float16[nchan])
```

```json
{
  "observation_id": 1527888, "station_id": 13, "client_version": "2.3.0",
  "t_ref": "2026-08-16T10:32:52.650048Z",
  "nchan": 1024, "samp_rate": 57600, "center_freq_hz": 435973500.0,
  "nfft_per_row": 5, "src_row_dt_s": 0.0888888,
  "decimation": 6, "row_dt_s": 0.5333333, "n_rows": 750,
  "f_min_hz": -28800.0, "bin_hz": 56.25,
  "dc_bins": [511, 512, 513],
  "units": "dB", "dtype": "float16", "raw": true,
  "png_axes": {
    "img_w": 841, "img_h": 1676,
    "left": 81, "top": 15, "width": 600, "height": 1546,
    "t_min": "2026-08-16T10:32:52.930Z", "t_max": "2026-08-16T10:39:09.100Z",
    "f_min_hz": -28800.0, "f_max_hz": 28743.75
  }
}
```

```
время строки j   = t_ref + tabs_us[j] / 1e6
частота канала k = f_min_hz + k · bin_hz
```

Объём при `nchan=1024` и шаге 0.5 с на проходе 400 с: 750 строк × 2056 байт
≈ 1.6 МБ, в gzip примерно вдвое меньше — сопоставимо с самим PNG (704 КБ).

### Требования к содержимому

- **сырой спектр, до косметики** — без удаления DC-выброса и без `PowerNorm`;
  DC-загрязнённые каналы просто перечислены в `dc_bins`;
- **прореживание усреднением линейной мощности**, не децибел: среднее логарифмов
  меньше логарифма среднего, и смещение тем больше, чем больше разброс — то есть
  именно на сигнале;
- **шаг 0.5 с** — при 200 Гц/с сигнал уходит примерно на 2 канала,
  размазывания почти нет; более мелкий шаг увеличивает объём без выигрыша;
- **`tabs` на каждую строку** — снимает всю неоднозначность по времени
  и делает ненужной калибровку по делениям оси;
- **`png_axes` в заголовке** — рамка осей в пикселях, нужна фронтенду,
  чтобы рисовать точки поверх картинки, и делает ненужной детекцию рамки.

## Отвергнутые варианты артефакта

**Только точная калибровка в метаданные PNG (~6 строк).** Минимальная правка,
снимает единственную невосстановимую величину `tabs[0]`. Но оставляет весь
пиксельный конвейер. Практически потеряло смысл: калибровка по делениям оси
проверена и решает ту же задачу вообще без правки клиента.

**Готовый трек со станции (~36 КБ).** Минимум трафика, но алгоритм извлечения
переезжает на станцию: его нельзя улучшить задним числом и нельзя пересчитать
с другими порогами. Станции — техника класса Raspberry Pi, отлаживать алгоритм
на парке невозможно.

**Полное сырьё (~18.5 МБ).** В 11 раз больше артефакта ради разрешения,
которое всё равно не используется: извлечение работает с шагом около секунды.

## Что это дало бы

- **Из сервиса ушли бы пять шагов**, каждый из которых остаётся источником
  тихих ошибок: детекция рамки осей, инверсия colormap, маскирование оверлеев,
  обработка DC-бланкирования, калибровка по делениям.
- `snr` стал бы настоящим отношением сигнал/шум в децибелах, а не монотонным прокси.
- Сервис перестал бы зависеть от вёрстки водопада: сейчас смена colormap,
  шага делений или добавление оверлея тихо ломает извлечение.
- **Широкополосные наблюдения (240 кГц) перестали бы быть слабым местом:**
  разрешение определялось бы каналом (234 Гц), а не пикселем (400 Гц).

## Почему отложено

Раздел на артефактах не заработает, пока новый клиент не раскатан на парк,
а прошлая раскатка (2.2.x) шла с июля по август и до конца не дошла — 7% станций
оставались на старых версиях. Пиксельный путь работает на 93% текущих наблюдений
сразу, без единой правки вне этого репозитория.

Кроме того, сырого файла водопада для проверки артефактного пути сейчас нет,
а пиксельный путь проверяется на любом свежем наблюдении из боевого API.

Хранение артефакта прорабатывалось отдельно — см. [012](012-artifact-storage.md),
тоже отложено.
