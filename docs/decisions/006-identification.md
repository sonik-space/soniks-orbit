# 006. Идентификация: автомат, от запуска к каталогу

## Контекст

Второй заявленный сценарий: сопоставить неопознанные объекты каталога с принятыми
сигналами. После кластерного запуска в каталоге появляются десятки объектов,
и неизвестно, какой из них твой.

В `rffit` для этого была клавиша `i` — перебор каталога с оценкой RMS.

СОНИКС уже умеет тянуть объекты запуска из Celestrak по INTDES
(`fetch_satellite_from_tle_source`), есть модель `Launch` и флаг `Satellite.unknown`.

### Стоимость

Скрининг **без фита элементов** — одна векторная прогонка SGP4 по точкам трека
на кандидата плюс профилирование несущей в замкнутом виде. Порядка 1.5 млн
вычислений SGP4 на наблюдение при полном каталоге — секунды векторизованным `sgp4`.

Замер фазы 6 подтвердил оценку: 2901 кандидат × 362 точки ≈ 1.05 млн
вычислений за **1.0–1.8 с**, обычным циклом по существующему `range_rate`,
без векторизации по кандидатам.

## Решение

Фоновая задача берёт наблюдения неопознанных объектов с сигналом.

1. **Скрининг без фита** по всему набору кандидатов, ранжирование по RMS.
   Сначала объекты того же запуска по INTDES — обычно этого достаточно;
   при неудаче весь активный каталог.
2. Результат — в очередь на подтверждение человеком.

### Полный фит топ-20 отменён замером фазы 6

Здесь стояла вторая ступень — честный фит топ-20 с приорами на элементы
каждого кандидата. Она **разрушает различимость**: после фита все 22 объекта
запуска приходят к RMS 0.020–0.025 кГц, и отрыв падает со ×177 до ×1.06
(на 1526877 — до ×1.00), то есть решение становится монеткой.

Причина в физике, а не в реализации. Объекты одного запуска делят плоскость
и период и различаются в основном фазой вдоль трассы, а приор на `argp + M`
равен 5° — ровно та свобода, которая нужна, чтобы сдвинуть любого из них
на ту же доплеровскую кривую. Из одного прохода наблюдаемы примерно две
величины, и фит принципиально не различает объекты, отличающиеся фазой.

Отсюда разделение по сценариям: **фит — инструмент уточнения**, и он
начинается после подтверждения, в созданной сессии. Идентификация
останавливается на скрининге.

## Отвергнуто

**Только объекты запуска.** Просто и быстро, но не помогает, когда объект
в каталоге не привязан к запуску или запуск неизвестен.

**Только по кнопке, без автомата.** Меньше кода и нет фоновой нагрузки,
но теряется заявленное «в автомате с коррекцией человека».

## Следствия

- Правильный объект обычно даёт RMS на порядок меньше остальных, поэтому
  ранжирования достаточно и человеку остаётся подтверждение. **Отрыв
  измеряется и показывается:** величина порядка единицы означает, что
  кандидаты неразличимы, и такое задание подаётся как «не определено»,
  а не списком кандидатов.
- **Проход по запуску нужен не только ради цены.** Замер: внутри запуска
  отрыв правильного объекта на порядок выше, чем по всему каталогу
  (×177 против ×18.9 на 1527888). Полный каталог тоже сходится, но
  различимость заметно хуже, а на границе применимости теряется совсем.
- **Победитель предварителен.** Соседние объекты каталога стоят близко,
  и перебор по новому наблюдению может назвать другого. Задание
  переписывается, пока человек его не решил.
- Нужен кеш активного каталога. Он оказался дешевле ожидаемого:
  `/api/latesttles/` отдаёт весь каталог **одним неразбитым ответом**
  (2901 объект, 1.1 МБ), а объекты запуска — фильтр по нему же.
- Извлечение трека в этом сценарии работает **без человека**, поэтому качество
  автоизвлечения напрямую определяет качество идентификации. Наблюдения,
  где извлечение ничего не нашло, просто не попадают в перебор.
- Подтверждение создаёт сессию с этим объектом как затравкой — то есть
  идентификация естественно перетекает в уточнение.
- Перед включением на боевом API надо убедиться, что нет лимита частоты запросов,
  который выбьет перебор масштаба каталога. **Проверено замером фазы 6:**
  глобального троттла у монолита нет, троттлится только `/api/latesttles/`
  (60/мин на IP, 429 ровно на 61-м запросе), а кешу нужен один запрос в час.
