# HTTP API

FastAPI, префикс `/api/v1`. Все маршруты требуют Keycloak JWT.
Схема OpenAPI отдаётся на `/openapi.json` — из неё генерируется клиент фронтенда,
см. [frontend.md](frontend.md).

Один маршрут — один файл, как в `soniks-backend/src/presentation/api/v2/routers/`.

Частоты в API — **герцы**. Время — ISO 8601 UTC. Килогерцы появляются только
в полях с суффиксом `_khz` (RMS, невязки), потому что так их показывает `rffit`
и так их привык читать оператор.

## Сессии

### `POST /api/v1/sessions`

```json
{ "name": "LOBACHEVSKY уточнение",
  "norad_id": 98423,
  "observation_ids": [1037258, 1039405],
  "seed": { "tle0": "...", "tle1": "...", "tle2": "..." } }
```

`seed` необязателен: по умолчанию берётся TLE первого наблюдения.
Извлечение треков ставится в очередь сразу. → `201`

### `GET /api/v1/sessions?limit`

Сессии вызывающего, новые сверху. `limit` по умолчанию 50.

```json
[ { "uuid": "...", "name": "...", "norad_id": 98423,
    "status": "draft", "n_observations": 5, "rms_khz": null } ]
```

Курсора нет: сессия — рабочая единица одного человека, их десятки, а не
тысячи. Заводить пагинацию имеет смысл, когда появится случай, а не заранее.
`rms_khz` — от последнего прогона фита любого статуса; `null`, пока фита
не было: до него у сессии нет числа, которое описывало бы её целиком.

### `GET /api/v1/sessions/{uuid}`

```json
{ "uuid": "...", "name": "...", "norad_id": 98423, "status": "fitted",
  "seed_tle": { "tle0": "...", "tle1": "...", "tle2": "..." },
  "observations": [
    { "observation_id": 1039405,
      "start": "2026-01-05T09:20:00Z", "end": "2026-01-05T09:28:00Z",
      "station_name": "Сампо-400 [R1NAV]", "ground_station": 13,
      "waterfall_url": "https://storage.yandexcloud.net/...",
      "max_altitude": 74.2,
      "extraction_status": "ok", "extraction_error": null, "n_points": 384,
      "rms_khz": 0.44, "carrier_hz": 435975120.5,
      "convention_margin": 224.9,
      "observation_frequency_hz": 435975000.0 } ],
  "latest_fit": { "fit_run_id": "...", "status": "ok", "rms_khz": 0.42,
                  "elements_out": { }, "tle": { } } }
```

До фита `rms_khz` и `carrier_hz` — это диагностика **извлечения**: невязка
относительно TLE самого наблюдения, где профилируется только несущая
и элементы не двигаются. `convention_margin` — запас между лучшей и следующей
конвенцией оси частот; порядок единицы означает, что варианты неразличимы,
то есть трек ненадёжен ([algorithms.md](algorithms.md) §3). При пустом треке
все три **null**, а не ноль.

`observation_frequency_hz` — частота наблюдения из ответа Django, рядом
с `center_freq_hz` калибровки, которая приходит из PNG-чанка. Сравнение делает
UI: расхождение показывается предупреждением, иначе несущая молча его поглотит.
На проверенных наблюдениях расхождения нет (открытый вопрос 4 закрыт),
но оба числа стоят рядом, и проверка бесплатна.

`latest_fit` — последний прогон **любого статуса**: у неуспешного тоже есть
элементы, и молчать о нём хуже, чем показать со статусом.

### `PUT /api/v1/sessions/{uuid}/seed`

Замена затравки ([decisions/014](decisions/014-mutable-seed.md)). **Ровно один**
из трёх ключей, два сразу — `422`:

```json
{ "tle": { "tle0": "LOBACHEVSKY", "tle1": "1 98423U...", "tle2": "2 98423..." } }
{ "elements": { "eccentricity": 0.0017, "epoch": "2026-01-05T09:24:33Z" } }
{ "template": "leo" }
```

`elements` накладывается **поверх** текущей затравки: незаданные поля
не трогаются. Кроме семи элементов принимает `epoch`, `satno`, `name`
и `intldes` — меню `c` из `rffit`. Частоты здесь нет: несущая своя
на каждое наблюдение и решается в замкнутом виде
([decisions/003](decisions/003-fit-engine.md)).

Правка `epoch` — перезапись поля, а **не** перенос элементов на новую эпоху.
Перенос — это `POST /fits/{id}/reepoch`.

`template` — `leo` / `gto` / `gso` / `heo`, таблица из `rffit.c:1092-1143`
(клавиша `t`). Ставится на середину набора; у `leo` восходящий узел
и средняя аномалия зависят от станции, поэтому наблюдениям сессии нужны
времена.

Строки в `tle` проверяются здесь же: длина, номер строки, контрольная сумма,
согласованность номера объекта, код ошибки SGP4. Иначе `400` — `twoline2rv`
мусор не отвергает, а молча возвращает нули.

→ `200` с сессией целиком. Прогоны фита не пересчитываются и не пересуживаются.

### `DELETE /api/v1/sessions/{uuid}`

→ `204`. Наблюдения и прогоны уходят каскадом, задания идентификации —
обнулением ссылки. `409`, если сессия опубликована: на неё ссылается
`Tle.url` в каталоге СОНИКС, и это единственный признак происхождения записи.

## Наблюдения в сессии

### `POST /api/v1/sessions/{uuid}/observations`

`{ "observation_ids": [1035076] }` → `202` с сессией целиком, извлечение
в очереди. Шаг 2 гайда. Уже входящие в сессию наблюдения пропускаются:
повторный вызов с тем же списком безвреден.

### `DELETE /api/v1/sessions/{uuid}/observations/{observation_id}`

→ `204`. Прогоны фита не трогаются: каждый хранит свой список наблюдений
и свои невязки (правило 10). `409` на последнем наблюдении — сессия без
наблюдений не черновик, а мусор.

### `GET /api/v1/sessions/{uuid}/observations/{observation_id}/track`

Параметр `?fit={uuid}` — прогон, по которому строится `model`. По умолчанию
последний. `404`, если такого прогона нет или он принадлежит другой сессии.

```json
{ "calibration": {
    "img_w": 841, "img_h": 1676,
    "plot_left": 81, "plot_top": 15, "plot_w": 600, "plot_h": 1546,
    "t_min": "2026-08-16T10:32:52.930Z", "t_max": "2026-08-16T10:39:09.100Z",
    "f_min_hz": -28800.0, "f_max_hz": 28743.75,
    "center_freq_hz": 435973500.0, "samp_rate": 57600, "nchan": 1024,
    "bin_hz": 56.25 },
  "waterfall_url": "https://storage.yandexcloud.net/...",
  "points": {
    "mjd": [], "f_abs_hz": [], "f_offset_hz": [],
    "snr": [], "weight": [], "enabled": [], "source": [] },
  "model": {
    "mjd": [], "f_offset_hz": [], "az_deg": [], "alt_deg": [],
    "t_ca": "2026-08-16T10:36:01.400Z", "t_epoch": "2026-08-15T20:14:46.400Z" },
  "extraction": { "status": "ok", "error": null } }
```

`calibration` — рамка осей, найденная сервисом, плюс параметры сетки.
Всё, что нужно фронту, чтобы обрезать картинку по рамке и линейно отображать
экран в данные. **Своей геометрии фронт не вычисляет и картинку не анализирует.**

`nchan` нужен потому, что `extent` задаёт координаты **центров** первого
и последнего канала, а не внешние края: без числа каналов отображение
пиксель → частота воспроизводится с постоянным сдвигом в полканала
([algorithms.md](algorithms.md) §1.5).

`model` — модельная кривая прогона фита на равномерной сетке времени водопада,
замена `ikhnosoniks`. Приходит она сюда, а не в ответ фита: рисуется поверх
этого водопада, и панель уже читает этот запрос. Считает её сервер по
`elements_out` и несущей прогона — фронт эфемерид не вычисляет (правило 9).
`null`, пока фита не было или пока нет калибровки.

`az_deg`/`alt_deg` — та же сетка в горизонтальных координатах: панель неба
рисуется прямо по ним, проекция `x = (90−alt)·sin az`, `y = −(90−alt)·cos az`.
`t_ca` — момент наибольшего сближения (`null`, если на этой сетке спутник
над горизонтом знак лучевой скорости не меняет), `t_epoch` — эпоха элементов.
Это вертикальные метки `T_CA` и `T_EP` из `rffit`.

**Наблюдение, которого в прогоне не было, кривую всё равно получает** — это
шаг 5 гайда, проверка TLE по стороннему проходу. Несущая берётся тремя
ступенями: из `per_observation` прогона; иначе решается в замкнутой форме
(decisions/003) по точкам самого наблюдения и элементам прогона; иначе
`observation_frequency` из снимка — тогда кривая встаёт со сдвигом, но форма
доплеровской ступеньки, ради которой её и смотрят, верна.

`status: "ok"` при пустом `points` — **нормальное** состояние, а не ошибка
(decisions/001): на корпусе так на 12 наблюдениях из 23.

### `PUT /api/v1/sessions/{uuid}/observations/{observation_id}/track`

Полная замена набора точек.

```json
{ "points": { "mjd": [], "f_offset_hz": [], "enabled": [], "source": [],
              "weight": [], "snr": [] } }
```

`f_abs_hz` **не принимается от клиента** — сервер вычисляет его сам одной
формулой ядра `domain/od/doppler.py::received_freq_hz` по замороженному
снимку наблюдения (правило 9 из
[ai-development-rules.md](ai-development-rules.md)). Ручная точка приходит с
`source: "manual"` и `f_offset_hz`. Все колонки обязаны быть одной длины,
`source` — только `auto` или `manual`.

`snr` необязателен: клиент получил его в `GET` и возвращает как есть.
Молча обнулять измеренную величину нельзя, поэтому при отсутствии
колонки ставятся нули.

Диагностика (`rms_khz`, `carrier_hz`, `convention_margin`) **пересчитывается**
по новому набору тем же кодом, что и при извлечении: до фазы 4 это
единственная обратная связь оператору о том, стало ли лучше. При пустом
наборе она снова `null`, а не ноль.

→ `200` с пересчитанным блоком точек.
`400`, если наблюдение ещё не откалибровано: центральная частота приходит
из PNG-чанка `satnogs:wf-dat` и до калибровки неизвестна.

Точки приходят только отсюда: автоматического поиска трека в системе нет
(decisions/015).

### `POST /api/v1/sessions/{uuid}/fits`

**Синхронный**, обычно менее секунды.

```json
{ "prior_sigmas": { "inclination_deg": 0.05, "raan_deg": 0.5,
                    "eccentricity": 0.001, "argp_deg": 20.0,
                    "mean_anomaly_deg": 20.0, "argp_plus_m_deg": 5.0,
                    "mean_motion_rev_day": 0.005, "bstar": 1e-4 },
  "f_scale": 0.5,
  "observation_ids": [1037258, 1039405],
  "free": "0101010",
  "priors_off": false }
```

Все поля необязательны; умолчания — из `core/configs/fit.py`.

`free` и `priors_off` — **экспертный режим**
([decisions/013](decisions/013-expert-mode.md)). Умолчание не изменилось:
все семь элементов свободны, слабо определённые удерживает приор
([decisions/004](decisions/004-regularization.md)).

`free` — семь символов `0`/`1` в порядке `inclination, raan, eccentricity,
argp, mean_anomaly, mean_motion, bstar`, зеркало клавиш 1–7 в `rffit`.
Зажатый параметр исключается из вектора оптимизации. Два шага гайда задаются
им буквально: `"0001000"` — только аргумент перигея, `"0101010"` — RAAN,
аргумент перигея и среднее движение.

`priors_off` — σ = ∞ по всем элементам. Взаимно исключается с `prior_sigmas`
(`422`). Маска из одних нулей — тоже `422`.

**Прогон с частичной маской UI обязан показывать иначе, чем полный**, ровно
по той же причине, что и `prior_dominated`: иначе четыре зажатых числа
читаются как подтверждённые данными.

Поля `compat` здесь **нет**. Режим совместимости (одна глобальная несущая,
приоры выключены, `loss='linear'`) живёт флагом в `domain/od/fit.py` и нужен
регрессионному тесту из [testing.md](testing.md) §1, а не оператору: он даёт
заведомо худший результат, и выводить его в UI значило бы предлагать его
как вариант.

```json
{ "fit_run_id": "...", "created_at": "2026-08-17T12:00:00Z", "status": "ok",
  "rms_khz": 0.42, "rms_pre_khz": 3.87, "n_points": 1240,
  "elements_in":  { "inclination_deg": 97.41, "...": 0, "epoch": "..." },
  "elements_out": { "inclination_deg": 97.4103, "...": 0, "epoch": "..." },
  "prior_dominated": ["eccentricity", "bstar"],
  "tle": { "tle0": "LOBACHEVSKY", "tle1": "1 98423U...", "tle2": "2 98423..." },
  "per_observation": [ { "observation_id": 1039405, "rms_khz": 0.44,
                         "carrier_hz": 435975120.5, "n": 384 } ],
  "residuals": { "1039405": { "mjd": [61268.4395, ...],
                              "residual_khz": [0.12, null, -0.31, ...] } },
  "config": { "prior_sigmas": { }, "priors_off": false, "free": "1111111",
              "f_scale": 0.5, "observation_ids": [ ],
              "n_points": 1240, "nfev": 41, "message": "..." } }
```

`prior_dominated` перечисляет элементы, которые данные не сдвинули — UI должен
показать их иначе, чем определённые, иначе оператор примет затравку за результат.
Имена там те же, что у `prior_sigmas`.

`residuals` индекс-в-индекс соответствует `points` того же наблюдения:
обе колонки блока длиной с `points`, а `residual_khz` равен `null` там, где
точка выключена. Ноль читался бы как измеренная невязка. `mjd` лежит рядом
затем, чтобы панель невязок не запрашивала треки всех наблюдений по отдельности:
ось времени у неё общая на весь набор, а треки читает панель водопада —
по одному, на активное наблюдение.

`status: "failed"` — прогон, где `least_squares` не сошёлся или исчерпал
`max_nfev`. Элементы, невязки и TLE в нём всё равно есть.

`config` сохраняется целиком в `od_fit_runs`: без приорных σ и `f_scale`
опубликованное TLE невоспроизводимо ([algorithms.md](algorithms.md) §4.3).

### `GET /api/v1/sessions/{uuid}/fits` — история прогонов

Строки **компактные**: `fit_run_id`, `created_at`, `status`, `rms_khz`,
`rms_pre_khz`, `n_points`, `elements_out`, `prior_dominated`. Без `residuals`
и `per_observation` — десять прогонов по 2500 точек это мегабайты на каждый
заход в раздел, а история нужна, чтобы выбрать прогон, а не разглядывать его.

## Публикация

### `POST /api/v1/fits/{fit_run_id}/reepoch`

Предпросмотр строк на другую эпоху. **Ничего не сохраняет.**

```json
{ "epoch_iso": "2026-01-05T09:23:57Z" }
```
или `{ "epoch_yyddd": "26005.391632037" }`, или
`{ "epoch": "latest_observation" }`. Ровно одно поле из трёх, иначе `422`.

`latest_observation` — конец последнего прохода, **участвовавшего в этом
прогоне**, из замороженного снимка наблюдения (правило 10). Наблюдения сессии,
не попавшие в прогон, эпоху не двигают: иначе она уехала бы туда, где данных
фита нет. Если у них нет времени окончания — `400`, а не молчаливая подстановка
эпохи прогона.

→ `{ "epoch": "2026-01-05T09:23:57Z",
      "tle": { "tle0": "...", "tle1": "...", "tle2": "..." } }`

`epoch` в ответе не для красоты: при `latest_observation` момент выбирает
сервер, и без него оператор не видит, куда попал.

### `POST /api/v1/fits/{fit_run_id}/publish`

```json
{ "mode": "publish", "reepoch_to": { "epoch": "latest_observation" } }
```

`reepoch_to` — то же тело, что у `reepoch`, и необязательно: без него
публикуется эпоха самого прогона. Одна форма на оба маршрута, а не строка
здесь и объект там: перенос считает один и тот же код, иначе предпросмотр
и опубликованное могли бы разойтись.

`mode`: `publish` — записать в каталог СОНИКС; `propose` — оставить
предложением. Предложение **до Django не доходит**: оно живёт у сервиса,
и человек с правами публикует тот же прогон позже.

Если вызывающий не владеет спутником, `mode` в ответе становится `propose`,
а `published_tle_id` — `null`.

**Порог качества проверяется на сервере до обращения к Django:**

| Условие | Значение |
|---|---|
| Прогон сошёлся | `status == "ok"` |
| RMS | ≤ 1.0 кГц |
| Точек | ≥ 100 |
| Наблюдений | ≥ 2 |
| Расхождение положения с затравкой на эпохе | ≤ 50 км |

→ `200 { "mode": "publish", "published_tle_id": 12345,
         "epoch": "...", "tle": { } }` ·
`403` нет прав · `409` не пройден порог, в теле — какое именно условие.

Источник записи в каталоге — **`Manual`**, и выбирает его монолит, а не сервис
и не клиент. `Manual` первый в `TLE_SOURCE_PRIORITY`, то есть публикация
выигрывает выбор TLE для всей сети немедленно, включая случай свежего
Space-Track.

Ослабление порогов — только вместе с правкой
[decisions/007-publishing.md](decisions/007-publishing.md).

### `GET /api/v1/publications?days=7`

Опубликованные и предложенные TLE, новые сверху. `days` по умолчанию 7,
допустимо от 1 до 90.

```json
[ { "fit_run_id": "...", "session_uuid": "...", "session_name": "LOBACHEVSKY",
    "norad_id": 98423, "published_at": "2026-08-17T15:58:52Z",
    "published_mode": "publish", "published_tle_id": 12345,
    "author_sub": "...", "rms_khz": 0.0344, "n_points": 579 } ]
```

Это админ-вид, который [decisions/007](decisions/007-publishing.md) требует
**до** первой боевой публикации. Он живёт здесь, а не в админке Django:
под источником `Manual` публикация фита неотличима от ручной строки, а весь
провенанс — прогон, наблюдения, RMS, автор — есть только у сервиса.

## Идентификация

Задания заводит почасовой сканер по наблюдениям неопознанных объектов
(decisions/006). Ручной запуск существует для оператора и демонстрации,
но автомат он не заменяет.

### `POST /api/v1/identifications`

`{ "observation_id": 1527888 }` → `202`, перебор в очереди.

### `GET /api/v1/identifications?stage=&limit=`

Задания, новые сверху. Параметр называется **`stage`**, а не `status`: так
называется колонка, и заводить второе имя тому же полю незачем. `limit`
по умолчанию 50.

Строки компактные: кандидаты урезаны до лучшего. Полный перебор по каталогу —
это тысячи строк на задание, а списку нужно решить, куда заходить.

```json
[ { "uuid": "...", "created_at": "...", "observation_id": 1527888,
    "stage": "screening", "margin": 177.4, "n_candidates": 22,
    "best": { }, "confirmed_norad_id": null, "session_uuid": null } ]
```

### `GET /api/v1/identifications/{uuid}`

```json
{ "uuid": "...", "observation_id": 1527888, "stage": "screening",
  "margin": 177.4,
  "candidates": [ { "norad_id": 64880, "name": "Geoscan-1",
                    "intdes": "25155E", "rms_khz": 0.0240,
                    "carrier_hz": 435976647.5, "same_launch": true,
                    "tle": { "tle0": "...", "tle1": "...", "tle2": "..." } } ],
  "confirmed_norad_id": null, "confirmed_by_sub": null, "session_uuid": null }
```

`margin` — во сколько раз лучший кандидат лучше следующего, и это **главное
число задания**. Ранжирования достаточно только потому, что правильный объект
даёт RMS на порядок меньше остальных; величина порядка единицы означает,
что кандидаты неразличимы и перебор ничего не решил. UI обязан подавать такое
задание как «не определено», а не как список кандидатов — та же форма
диагностики, что `convention_margin` у выбора оси частот. `null` — перебора
не было; ноль читался бы как «неразличимо», а это другое состояние.

Поля `stage` у кандидата **нет**: элементы не двигаются ни у одного из них.
Полный фит топ-20 отменён замером — он роняет отрыв со ×177 до ×1.06
([algorithms.md](algorithms.md) §6), и фит начинается только после
подтверждения, в созданной сессии.

Строки TLE отдаются наружу затем же, зачем хранятся: затравкой сессии идёт
та строка, по которой считался показанный RMS.

**Победитель предварителен.** Соседние объекты каталога стоят близко, и перебор
по новому наблюдению может назвать другого; задание переписывается, пока
человек его не решил.

### `GET /api/v1/identifications/{uuid}/track`

Та же форма, что у трека наблюдения сессии: `calibration`, `waterfall_url`,
`points`, `model`. Панель водопада на фронте одна и та же, а сессии у задания
ещё нет.

`model` — кривая **лучшего кандидата**, посчитанная сервером по сохранённым
в задании строкам (правило 9). Именно она отвечает на вопрос «а похоже ли»,
ради которого водопад в этом разделе и показывается. Рядом `norad_id` —
чей это объект.

### `POST /api/v1/identifications/{uuid}/confirm`

`{ "norad_id": 64880 }` → `{ "session_uuid": "..." }` — создаётся сессия
с этим объектом как затравкой: идентификация перетекает в уточнение.

Наблюдение переезжает в сессию вместе с готовыми калибровкой, точками
и диагностикой — извлечение уже отработало при переборе, и второй раз
качать водопад незачем. `409`, если задание уже решено.

### `POST /api/v1/identifications/{uuid}/reject`

→ `204`. Отклонённое задание повторный перебор больше не трогает.

## Ошибки

Формат — как в `soniks-backend`. Значимые коды:

| Код | Когда |
|---|---|
| `422` | у водопада нет `satnogs:wf-dat`; не найдена рамка осей или colorbar |
| `409` | не пройден порог качества при публикации; у сессии нет номера объекта |
| `403` | нет прав на публикацию для этого спутника |
| `400` | меньше 20 включённых точек или меньше 2 наблюдений для фита |

Отдельно про `422` из-за отсутствия `satnogs:wf-dat`: это **ожидаемое** состояние
для наблюдений до июля 2026 и для станций на клиентах старше 2.2.x.
UI должен объяснять причину, а не показывать ошибку.
