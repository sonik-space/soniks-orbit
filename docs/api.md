# HTTP API

FastAPI, префикс `/api/v1`. Все маршруты требуют Keycloak JWT.
Схема OpenAPI отдаётся на `/openapi.json` — из неё генерируется клиент фронтенда,
см. [frontend.md](frontend.md).

Один маршрут — один файл, как в `soniks-backend/src/presentation/api/v2/routers/`.

Частоты в API — **герцы**. Время — ISO 8601 UTC. Килогерцы появляются только
в полях с суффиксом `_khz` (RMS, невязки), потому что так их показывает `rffit`
и так их привык читать оператор.

## Сессии

### `POST /api/v1/sessions`

```json
{ "name": "LOBACHEVSKY уточнение",
  "norad_id": 98423,
  "observation_ids": [1037258, 1039405],
  "seed": { "tle0": "...", "tle1": "...", "tle2": "..." } }
```

`seed` необязателен: по умолчанию берётся TLE первого наблюдения.
Извлечение треков ставится в очередь сразу. → `201`

### `GET /api/v1/sessions?limit`

Сессии вызывающего, новые сверху. `limit` по умолчанию 50.

```json
[ { "uuid": "...", "name": "...", "norad_id": 98423,
    "status": "draft", "n_observations": 5, "rms_khz": null } ]
```

Курсора нет: сессия — рабочая единица одного человека, их десятки, а не
тысячи. Заводить пагинацию имеет смысл, когда появится случай, а не заранее.
`rms_khz` — от последнего прогона фита любого статуса; `null`, пока фита
не было: до него у сессии нет числа, которое описывало бы её целиком.

### `GET /api/v1/sessions/{uuid}`

```json
{ "uuid": "...", "name": "...", "norad_id": 98423, "status": "fitted",
  "seed_tle": { "tle0": "...", "tle1": "...", "tle2": "..." },
  "observations": [
    { "observation_id": 1039405,
      "start": "2026-01-05T09:20:00Z", "end": "2026-01-05T09:28:00Z",
      "station_name": "Сампо-400 [R1NAV]", "ground_station": 13,
      "waterfall_url": "https://storage.yandexcloud.net/...",
      "max_altitude": 74.2,
      "extraction_status": "ok", "extraction_error": null, "n_points": 384,
      "rms_khz": 0.44, "carrier_hz": 435975120.5,
      "convention_margin": 224.9,
      "observation_frequency_hz": 435975000.0 } ],
  "latest_fit": { "fit_run_id": "...", "status": "ok", "rms_khz": 0.42,
                  "elements_out": { }, "tle": { } } }
```

До фита `rms_khz` и `carrier_hz` — это диагностика **извлечения**: невязка
относительно TLE самого наблюдения, где профилируется только несущая
и элементы не двигаются. `convention_margin` — запас между лучшей и следующей
конвенцией оси частот; порядок единицы означает, что варианты неразличимы,
то есть трек ненадёжен ([algorithms.md](algorithms.md) §3). При пустом треке
все три **null**, а не ноль.

`observation_frequency_hz` — частота наблюдения из ответа Django, рядом
с `center_freq_hz` калибровки, которая приходит из PNG-чанка. Сравнение делает
UI: расхождение показывается предупреждением, иначе несущая молча его поглотит.
На проверенных наблюдениях расхождения нет (открытый вопрос 4 закрыт),
но оба числа стоят рядом, и проверка бесплатна.

`latest_fit` — последний прогон **любого статуса**: у неуспешного тоже есть
элементы, и молчать о нём хуже, чем показать со статусом.

### `GET /api/v1/sessions/{uuid}/observations/{observation_id}/track`

```json
{ "calibration": {
    "img_w": 841, "img_h": 1676,
    "plot_left": 81, "plot_top": 15, "plot_w": 600, "plot_h": 1546,
    "t_min": "2026-08-16T10:32:52.930Z", "t_max": "2026-08-16T10:39:09.100Z",
    "f_min_hz": -28800.0, "f_max_hz": 28743.75,
    "center_freq_hz": 435973500.0, "samp_rate": 57600, "nchan": 1024,
    "bin_hz": 56.25 },
  "waterfall_url": "https://storage.yandexcloud.net/...",
  "points": {
    "mjd": [], "f_abs_hz": [], "f_offset_hz": [],
    "snr": [], "weight": [], "enabled": [], "source": [] },
  "model": { "mjd": [], "f_offset_hz": [] },
  "extraction": { "status": "ok", "error": null } }
```

`calibration` — рамка осей, найденная сервисом, плюс параметры сетки.
Всё, что нужно фронту, чтобы обрезать картинку по рамке и линейно отображать
экран в данные. **Своей геометрии фронт не вычисляет и картинку не анализирует.**

`nchan` нужен потому, что `extent` задаёт координаты **центров** первого
и последнего канала, а не внешние края: без числа каналов отображение
пиксель → частота воспроизводится с постоянным сдвигом в полканала
([algorithms.md](algorithms.md) §1.5).

`model` — модельная кривая последнего прогона фита на равномерной сетке
времени водопада, замена `ikhnosoniks`. Приходит она сюда, а не в ответ фита:
рисуется поверх этого водопада, и панель уже читает этот запрос. Считает её
сервер по `elements_out` и несущей прогона — фронт эфемерид не вычисляет
(правило 9). `null`, пока фита не было, пока наблюдение в нём не участвовало
или пока нет калибровки.

`status: "ok"` при пустом `points` — **нормальное** состояние, а не ошибка
(decisions/001): на корпусе так на 12 наблюдениях из 23.

### `PUT /api/v1/sessions/{uuid}/observations/{observation_id}/track`

Полная замена набора точек.

```json
{ "points": { "mjd": [], "f_offset_hz": [], "enabled": [], "source": [],
              "weight": [], "snr": [] } }
```

`f_abs_hz` **не принимается от клиента** — сервер вычисляет его сам одной
формулой ядра `domain/od/doppler.py::received_freq_hz` по замороженному
снимку наблюдения (правило 9 из
[ai-development-rules.md](ai-development-rules.md)). Ручная точка приходит с
`source: "manual"` и `f_offset_hz`. Все колонки обязаны быть одной длины,
`source` — только `auto` или `manual`.

`snr` необязателен: клиент получил его в `GET` и возвращает как есть.
Молча обнулять измеренную величину нельзя, поэтому при отсутствии
колонки ставятся нули.

Диагностика (`rms_khz`, `carrier_hz`, `convention_margin`) **пересчитывается**
по новому набору тем же кодом, что и при извлечении: до фазы 4 это
единственная обратная связь оператору о том, стало ли лучше. При пустом
наборе она снова `null`, а не ноль.

→ `200` с пересчитанным блоком точек.
`400`, если наблюдение ещё не откалибровано: центральная частота приходит
из PNG-чанка `satnogs:wf-dat` и до извлечения неизвестна.

### `POST /api/v1/sessions/{uuid}/observations/{observation_id}/reextract`

```json
{ "snr_threshold": 4.0, "bin_seconds": 1.0 }
```

Перезапуск автоизвлечения с другими параметрами; оба поля необязательны,
умолчания — из `core/configs/waterfall.py`. → `202`.
Ручные точки при этом сохраняются, автоматические заменяются, порядок
восстанавливается по `mjd`.

Поля `peak_width_tolerance` здесь **нет**. Здесь стояло
`[0.3, 4.0]` — множители к `w_exp = bw_99_hz / samp_rate · Wp` из
[algorithms.md](algorithms.md) §2, — и замер фазы 1 эту параметризацию
отверг: `bw_99_hz` описывает занятую полосу всего сигнала, а гребень это
одна линия шириной 1..7 px, так что нижняя граница `0.3·146 = 44 px`
отбрасывала все строки до единой. Границы считает
`domain/waterfall/ridge.py::peak_width_limits_px` из разрешения рендера
и потолка узкополосности, и наружу ручки к ним не выведено.

## Фит

### `POST /api/v1/sessions/{uuid}/fits`

**Синхронный**, обычно менее секунды.

```json
{ "prior_sigmas": { "inclination_deg": 0.05, "raan_deg": 0.5,
                    "eccentricity": 0.001, "argp_deg": 20.0,
                    "mean_anomaly_deg": 20.0, "argp_plus_m_deg": 5.0,
                    "mean_motion_rev_day": 0.005, "bstar": 1e-4 },
  "f_scale": 0.5,
  "observation_ids": [1037258, 1039405] }
```

Все поля необязательны; умолчания — из `core/configs/fit.py`.

Поля `compat` здесь **нет**. Режим совместимости (одна глобальная несущая,
приоры выключены, `loss='linear'`) живёт флагом в `domain/od/fit.py` и нужен
регрессионному тесту из [testing.md](testing.md) §1, а не оператору: он даёт
заведомо худший результат, и выводить его в UI значило бы предлагать его
как вариант. Галочек заморозки параметров нет по
[decisions/004](decisions/004-regularization.md).

```json
{ "fit_run_id": "...", "created_at": "2026-08-17T12:00:00Z", "status": "ok",
  "rms_khz": 0.42, "rms_pre_khz": 3.87, "n_points": 1240,
  "elements_in":  { "inclination_deg": 97.41, "...": 0, "epoch": "..." },
  "elements_out": { "inclination_deg": 97.4103, "...": 0, "epoch": "..." },
  "prior_dominated": ["eccentricity", "bstar"],
  "tle": { "tle0": "LOBACHEVSKY", "tle1": "1 98423U...", "tle2": "2 98423..." },
  "per_observation": [ { "observation_id": 1039405, "rms_khz": 0.44,
                         "carrier_hz": 435975120.5, "n": 384 } ],
  "residuals": { "1039405": { "mjd": [61268.4395, ...],
                              "residual_khz": [0.12, null, -0.31, ...] } },
  "config": { "prior_sigmas": { }, "f_scale": 0.5, "observation_ids": [ ],
              "n_points": 1240, "nfev": 41, "message": "..." } }
```

`prior_dominated` перечисляет элементы, которые данные не сдвинули — UI должен
показать их иначе, чем определённые, иначе оператор примет затравку за результат.
Имена там те же, что у `prior_sigmas`.

`residuals` индекс-в-индекс соответствует `points` того же наблюдения:
обе колонки блока длиной с `points`, а `residual_khz` равен `null` там, где
точка выключена. Ноль читался бы как измеренная невязка. `mjd` лежит рядом
затем, чтобы панель невязок не запрашивала треки всех наблюдений по отдельности:
ось времени у неё общая на весь набор, а треки читает панель водопада —
по одному, на активное наблюдение.

`status: "failed"` — прогон, где `least_squares` не сошёлся или исчерпал
`max_nfev`. Элементы, невязки и TLE в нём всё равно есть.

`config` сохраняется целиком в `od_fit_runs`: без приорных σ и `f_scale`
опубликованное TLE невоспроизводимо ([algorithms.md](algorithms.md) §4.3).

### `GET /api/v1/sessions/{uuid}/fits` — история прогонов

Строки **компактные**: `fit_run_id`, `created_at`, `status`, `rms_khz`,
`rms_pre_khz`, `n_points`, `elements_out`, `prior_dominated`. Без `residuals`
и `per_observation` — десять прогонов по 2500 точек это мегабайты на каждый
заход в раздел, а история нужна, чтобы выбрать прогон, а не разглядывать его.

## Публикация

### `POST /api/v1/fits/{fit_run_id}/reepoch`

```json
{ "epoch_iso": "2026-01-05T09:23:57Z" }
```
или `{ "epoch_yyddd": "26005.391632037" }`, или
`{ "epoch": "latest_observation" }`.

→ `{ "tle": { "tle0": "...", "tle1": "...", "tle2": "..." } }`

### `POST /api/v1/fits/{fit_run_id}/publish`

```json
{ "mode": "publish", "reepoch_to": "latest_observation" }
```

`mode`: `publish` — записать в каталог СОНИКС с источником `Fitted`;
`propose` — отправить на модерацию.

Если вызывающий не владеет спутником, `mode` принудительно становится `propose`.

**Порог качества проверяется на сервере до обращения к Django:**

| Условие | Значение |
|---|---|
| RMS | ≤ 1.0 кГц |
| Точек | ≥ 100 |
| Наблюдений | ≥ 2 |
| Расхождение положения с затравкой на эпохе | ≤ 50 км |

→ `200 { "published_tle_id": 12345 }` · `403` нет прав ·
`409` не пройден порог, в теле — какое именно условие.

Ослабление порогов — только вместе с правкой
[decisions/007-publishing.md](decisions/007-publishing.md).

## Ошибки

Формат — как в `soniks-backend`. Значимые коды:

| Код | Когда |
|---|---|
| `422` | у водопада нет `satnogs:wf-dat`; не найдена рамка осей или colorbar |
| `409` | не пройден порог качества при публикации |
| `403` | нет прав на публикацию для этого спутника |
| `400` | меньше 20 включённых точек или меньше 2 наблюдений для фита |

Отдельно про `422` из-за отсутствия `satnogs:wf-dat`: это **ожидаемое** состояние
для наблюдений до июля 2026 и для станций на клиентах старше 2.2.x.
UI должен объяснять причину, а не показывать ошибку.
