## 1. Калибровка водопада

Единственный источник данных — отрендеренный PNG. Сырых спектров сеть не хранит,
и выгружать их со станций мы сейчас не будем — см.
[decisions/002-pixel-only.md](decisions/002-pixel-only.md).

### 1.1 Метаданные PNG

Клиент сохраняет водопад через `matplotlib.savefig(metadata=...)`, поэтому
в текстовых чанках PNG лежит точная калибровка. Проверено на боевом наблюдении 1527888:

```json
"satnogs:wf-dat":    {"timestamp":"2026-08-16T10:32:52.650048Z","nchan":"1024",
                      "samp_rate":"57600","nfft_per_row":"5",
                      "center_freq":"435973500.0","endianness":"1"}
"satnogs:wf-signal": {"modulation":"2-FSK / wide-FSK","deviation_hz":4801.6,
                      "deviation_confidence":1.0,"snr_db":27.33,"bw_99_hz":14062.5}
```

```python
row_dt_s = nfft_per_row * nchan / samp_rate        # 0.0889 с на строку данных
bin_hz   = samp_rate / nchan                       # 56.25 Гц на канал
```

**Полоса равна `samp_rate`.** Эвристика `48e3` из старого инструмента
(в комментарии честно помечена как «very bad heuristic, will fail in many cases»)
не нужна.

Если `satnogs:wf-dat` отсутствует — **падаем громко**. Эвристического отката нет:
наблюдение без метаданных непригодно, а молчаливая догадка о полосе даст
правдоподобный, но неверный результат. Поле `satnogs_rx_samp_rate` у станции
через API не отдаётся, так что взять полосу больше неоткуда.

### 1.2 Ось частот несимметрична

Клиент строит сетку частот как

```python
freq = np.linspace(-0.5*samp_rate, 0.5*samp_rate, nchan, endpoint=False)
fmin, fmax = freq[0]/1000, freq[-1]/1000        # кГц, это и идёт в extent
```

Из-за `endpoint=False` последний канал — это `samp_rate/2 − bin_hz`, а не
`+samp_rate/2`:

```
f_min_hz = -samp_rate/2
f_max_hz = +samp_rate/2 - bin_hz
```

Наивное симметричное `±samp_rate/2` даёт постоянное смещение `+bin_hz/2` ≈ 28 Гц.
Оно полностью поглощается несущей наблюдения, то есть на фит не влияет,
но абсолютная частота в UI была бы смещена.

Переменная в коде клиента называется `_freq_crop`, а комментарий говорит про
«обрезку краёв SDR» — обрезки на самом деле нет, это остаточное имя.
Не принимать его за реальное сужение полосы.

### 1.3 Детекция рамки осей

Изображение сохранено с `bbox_inches="tight"`, поэтому положение области графика
плавает от картинки к картинке (замерено 823×1603, 832×1603 и 841×1676).
Хардкодить координаты нельзя — старый инструмент делал именно это, и ошибался.

Наивный поиск «тёмных пикселей» не работает: нижний конец colormap тоже тёмный.
Работает **ахроматичность** — линии осей чёрные и ненасыщенные, а colormap насыщен:

```python
mx, mn = a.max(axis=2), a.min(axis=2)
spine  = (mx < 90) & ((mx - mn) < 20)

col_frac = spine.sum(axis=0) / H
row_frac = spine.sum(axis=1) / W
Vc = центры серий, где col_frac > 0.6
Rc = центры серий, где row_frac > 0.6

plot_left, plot_right = пара из Vc с максимальным разносом
plot_top,  plot_bot   = пара из Rc с максимальным разносом
cb_left,   cb_right   = следующая по ширине пара правее plot_right, ширина 10..60 px
```

Проверено: на `ikhnosoniks/temp/*.png` даёт колонки `[66, 686, 724, 755]`
и строки `[10, 1550]` на **обоих** изображениях разного размера; на боевом
водопаде 841×1676 — колонки `[81, 681, 743, 763]`, строки `[15, 1561]`.
Область графика — 600–620 px, colorbar — 20–31 px, поэтому выбор «пары
с максимальным разносом» отсекает colorbar по построению.

Проверки: обе стороны области больше 30% размера изображения; внутренность
не белая более чем на 90% (защита от неудавшегося рендера).

### 1.4 Ось времени: калибровка по делениям

Разбор `soniks-client-new/src/soniks_client/waterfall.py`:

```python
tmin = np.min(wf_data['data']['tabs'] / 10**6)     # tabs — метки строк, мкс
tmax = np.max(wf_data['data']['tabs'] / 10**6)
t_ref  = datetime.strptime(metadata['timestamp'], ...)
dt_min = t_ref + timedelta(seconds=tmin)
dt_max = t_ref + timedelta(seconds=tmax)
extent = [fmin, fmax, date2num(dt_min), date2num(dt_max)]
```

Границы оси — это метки **первой и последней строки данных**, а не
`t0 + n_rows·row_dt` и не `observation.end`.

**Проблема: `tabs[0]` в метаданные PNG не попадает.** Там есть только `timestamp`,
то есть `t_ref`, а `dt_min = t_ref + tabs[0]`. На проверенном наблюдении
`tabs[0] ≈ 0.28 с` — при скорости изменения доплера ~200 Гц/с это **~56 Гц
систематики**, своей у каждого наблюдения. Из одних метаданных ось времени
восстановить нельзя.

**Решение — калибровка по делениям оси.** Клиент ставит их
`MinuteLocator(interval=INTERVAL_IN_MINUTES)` (по умолчанию 1), то есть строго
на целых минутах. Деления — короткие ахроматичные штрихи слева от левой границы,
детектируются тем же признаком, что и рамка.

Проверено на боевом водопаде: **7 делений, шаг ровно 246.0 px, разброс нулевой.**
Значит 246 px = 60 с, а абсолютная привязка следует из того, что деления —
целые минуты, а `t_ref` даёт грубую оценку в пределах ±30 с.

Шаг делений **выводится из данных**, а не берётся равным минуте: при длинном
проходе `MinuteLocator` может выбрать другой интервал. Двух делений достаточно,
чтобы получить и масштаб, и смещение; OCR подписей не нужен.

Если делений меньше двух (очень короткий проход) — откат на `t_ref` с явным
предупреждением, что возможна систематика до ~0.3 с.

### 1.5 Отображение пиксель → (время, частота)

`extent` задаёт **внешние края** нарисованного массива, а его границы — это
координаты **центров** первого и последнего элемента. Поэтому элемент `j`
из `n` рисуется по центру доли `(j + 0.5)/n`, и обратное преобразование
из доли `v` в индекс данных: `j = v·n − 0.5`.

```
u = (j_px + 0.5) / Wp
f_offset_hz = -samp_rate/2 + (u·nchan − 0.5) · bin_hz

v = (i_px + 0.5) / Hp                       # i_px считается снизу, origin='lower'
t = dt_min + (v·n_rows − 0.5) · (dt_max − dt_min) / (n_rows − 1)
```

Поправка на полэлемента по времени даёт максимум ~0.044 с на краях,
то есть ~9 Гц — меньше пиксельного квантования, но она бесплатна.

**Итоговое разрешение:**

| Ось | На пиксель | В герцах при 200 Гц/с |
|---|---|---|
| Частота, полоса 57.6 кГц | 96 Гц | 96 Гц |
| Частота, полоса 240 кГц | **400 Гц** | **400 Гц** |
| Время | 0.244 с | ~49 Гц |
| Поправка на полэлемента | — | ~9 Гц |
| `tabs[0]` без калибровки по делениям | — | ~56 Гц |

Рендер прореживает данные по времени (~2.7 строки на пиксель при `row_dt=0.0889`),
поэтому разрешение по времени определяется пикселем, а не строкой.

Полоса 240 кГц — самый слабый случай: 400 Гц/пиксель уже сопоставимы с RMS фита.
Таких наблюдений около 1.5%. Это один из аргументов держать артефакт как
возможное развитие, см. [decisions/011](decisions/011-spectrum-artifact.md).

### 1.6 Интенсивность: colorbar как готовый LUT

**Ключевая находка: colorbar на самом изображении — это точная таблица цветов.**
Не нужно знать ни имя colormap, ни параметры `PowerNorm`.

На проверенном образце полоса даёт ровно 256 уникальных цветов, монотонных
от `(64,0,79)` через `(33,144,141)` к `(239,218,34)` — то есть viridis,
а вовсе не `jet`, как можно было предположить. Это и есть аргумент
никогда не хардкодить colormap.

```python
lut = colorbar_interior.mean(axis=1)[::-1]           # (N, 3), индекс 0 = минимум
d, idx = cKDTree(lut).query(interior.reshape(-1, 3))
z       = (idx / (len(lut) - 1)).reshape(Hp, Wp)     # монотонно по мощности
overlay = (d > 30).reshape(Hp, Wp)
z[overlay] = np.nan
```

Поиску гребня нужен только **монотонный** прокси мощности, а не абсолютные дБ,
поэтому неизвестная `PowerNorm(gamma=1.4)` не мешает.

**Расстояние до ближайшей записи LUT бесплатно детектирует оверлеи** — маркеры
декодированных кадров, доплеровские кривые мешающих спутников, аннотацию девиации.
Замер на боевом водопаде: 0.18% пикселей.

Если пара colorbar не найдена — **исключение**, не догадка о colormap.

### 1.7 Что ещё делает клиент с картинкой

Из `waterfall.py` и `core/configs/waterfall.py`:

**Удаление DC-выброса.** Три центральных канала заменяются полусуммой соседей:

```python
center_bin = spec.shape[1] // 2
for dr in [-1, 0, 1]:
    spec_plot[:, center_bin+dr] = (spec_plot[:, center_bin-2] + spec_plot[:, center_bin+2]) / 2
```

3 канала из 1024 — это ~1.8 пикселя в центре области графика. Данные там
**синтетические**. Существенно потому, что при хорошем опорном TLE остаток
доплера проходит через нулевое смещение именно вблизи TCA, то есть в самой
информативной точке. Маскировать ±2 px вокруг центральной колонки и считать
разрывом, а не данными.

Замер: профиль в центре просаживается с ~0.0126 до ~0.0107 — эффект есть,
но это сглаживание, а не дыра, поэтому без явной маски автоматика его не заметит.

**Размытия нет.** `_gaussian_blur2d` в клиенте определён, но **не вызывается** —
мёртвый код. Единственная модификация спектра перед отрисовкой это зануление
DC-каналов, поэтому картинка достаточно честный рендер.

**Перекрестье по умолчанию выключено** (`HELP_LINES = False`), так что красных
линий в центре обычно нет. Маскирование оверлеев всё равно нужно.

**Нормировка фиксированная** (`AUTORANGE = False`, `MIN_VALUE = -110`,
`MAX_VALUE = -50`, `PowerNorm(gamma=1.4)`). Значит индекс в LUT восстанавливается
в **абсолютные дБ**:

```
dB = vmin + (vmax − vmin) · (idx / (N−1))^(1/γ)
```

Для поиска гребня это не нужно, но SNR можно выдавать в настоящих децибелах
и сверять с `snr_db` из `satnogs:wf-signal`. Если `AUTORANGE` где-то включён,
границы неизвестны, и остаётся монотонный прокси.

### 1.8 Пригодность наблюдения

`satnogs:wf-dat` пишет только клиент **2.2.x, появившийся около июля 2026**.
Замеры: на выборках 2024-07, 2025-07, 2026-03 и 2026-07-01 — ноль из шести-восьми.
На 67 свежих наблюдениях метаданные есть у 62 (93%); остальные приходят
со станций на 2.1.0 и 1.2.8.

Практический вывод: **раздел работает со свежими наблюдениями, история
до июля 2026 непригодна**. Оба сценария опираются на свежие данные, так что
это приемлемо, но UI обязан объяснять причину, а не показывать ошибку.

## 2. Извлечение гребня

```
B = max(1, round(Hp / duration_s))               # биннинг до ~1 точки в секунду
Z = nanmean(z.reshape(Hp // B, B, Wp), axis=1)   # поднимает SNR перед поиском пика

w_exp = bw_99_hz / samp_rate * Wp                # ожидаемая ширина сигнала, px

для каждой строки r:
    b     = median_filter(Z[r], size=101)        # фон вдоль частоты
    sigma = 1.4826 · median(|Z[r] − b|)          # робастная оценка шума
    snr   = (Z[r] − b) / sigma
    пики  = до 2 локальных максимумов, разнесённых более чем на 3·w_exp
    оставить пики с snr ≥ 4.0 и шириной по половине высоты в [0.3, 4.0]·w_exp
    субпиксель: j* = Σ(j · snr_j) / Σ snr_j по окну, где snr > 0.5·snr_пика
    вес: w = min(1.0, snr_пика / 10.0)
```

Затем **робастная трассировка**: RANSAC-подгонка кубики по времени к сильнейшему
пику каждой строки (минимум 30% инлайеров), отсев точек дальше 3σ и участков,
где частота растёт быстрее шума — доплеровская S-кривая монотонно убывает.

**Субпиксель центроидом, а не параболой по трём точкам.** Билинейный ресемплинг
при рендере размазывает пик на ~`Wp/nchan` ≈ 0.6 px и делает плечи асимметричными;
центроид по окну выше половины высоты деградирует мягче.

```python
# ponytail: RANSAC-кубика вместо динамического программирования по кандидатам.
#           Апгрейд до DP (цена = -snr + λ·max(0, f_j - f_prev) плюс цена пропуска),
#           если реально встретятся проходы с двумя спутниками в полосе.
#           Человек их и так может поправить руками.
```

### Режимы отказа

| Ситуация | Поведение | Правильно ли |
|---|---|---|
| Слабый проход | мало строк выше порога, разреженный трек | да, человек дорисует |
| Стационарная помеха (вертикальная линия) | отсекается монотонностью и RANSAC | да |
| Два спутника в полосе | возвращается один трек | приемлемо, человек правит |
| Широкополосный сигнал | тест ширины отбрасывает всё, трек пуст | приемлемо, цель — узкополосные |
| Оверлей поверх сигнала | строки замаскированы, разрыв в треке | да, разрыв лучше неверной точки |
| Сигнал в DC-каналах | разрыв вблизи нулевого смещения | да, разрыв лучше синтетической точки |

UI обязан подавать «извлечение ничего не нашло» как **нормальное** состояние
с очевидной кнопкой ручной разметки, иначе гибридная автоматизация не работает.

## 3. Абсолютная частота

Клиент снимал доплер по опорному TLE во время записи, поэтому на оси отложен остаток.
Возвращаем доплер обратно:

```
v_r(t) = range_rate(TLE_наблюдения, станция, t)          # км/с
f_abs_hz = center_freq_hz + f_offset_hz(t) − center_freq_hz · v_r(t) / C_KM_S
```

TLE берётся из `obs["tle"]` в JSON API — **не** выскребается со страницы регуляркой,
как делали старые инструменты.

`f_abs_hz` — это принятая частота на площадке, ровно то, что потребляет `rffit`.

### Положение наблюдателя

Должно совпадать со `strf/rffit.c:1459` (`obspos_xyz`), иначе регрессионный тест
не сойдётся:

```
sl = sin(lat);  ff = sqrt(1 − FLAT·(2−FLAT)·sl²)
gc = 1/ff + alt_km/XKMPER
gs = (1−FLAT)²/ff + alt_km/XKMPER
theta  = gmst(mjd) + lon
dtheta = dgmst(mjd) · π/180 / 86400

pos = (gc·cos(lat)·cos(theta), gc·cos(lat)·sin(theta), gs·sin(lat)) · XKMPER
vel = (−gc·cos(lat)·sin(theta), gc·cos(lat)·cos(theta), 0) · XKMPER · dtheta

gmst(mjd) = (280.46061837 + 360.98564736629·(mjd − 51544.5)
             + T²·(0.000387933 − T/38710000)) mod 360,   T = (mjd − 51544.5)/36525
```

**Высота станции: Django API отдаёт метры, strf работает в километрах.**

`range_rate` — проекция разности скоростей спутника и наблюдателя на единичный
вектор «наблюдатель → спутник». Положение спутника — SGP4 в TEME, через
`mjd + 2400000.5` как юлианскую дату.

## 4. Фит

### 4.1 Параметры

```
a = [incl°, RAAN°, ecc, argp°, M°, n об/сут, B*]
p_j = (a_j − a_seed_j) / σ_j                    ← оптимизируется это
```

Углы разворачиваются в (−180, 180] перед делением. Масштабирование встроено
в параметризацию, поэтому `x_scale=1.0`, а априорный член получается бесплатно.

Зажимы внутри функции невязок, как в `chisq` (`rffit.c:1645`):
`ecc → [0, 0.999)`, `n ≥ 0.05`.

### 4.2 Вектор невязок

Для наблюдения `k` с точками `I_k`, измеренными частотами `f_i` (кГц) и весами `w_i`:

```
v_i   = range_rate(a, mjd_i, станция_k)          одна векторная прогонка SGP4 на наблюдение
fac_i = 1 − v_i / C_KM_S

F_k   = Σ_{i∈I_k} w_i·fac_i·f_i  /  Σ_{i∈I_k} w_i·fac_i²      ← несущая, СВОЯ на наблюдение
r_i   = √w_i · (f_i − fac_i·F_k)                               ← кГц
```

Это в точности `sum1/sum2` из `rffit.c:1687`, обобщённое с одной глобальной несущей
на одну на наблюдение. `F_k` не является свободным параметром — она профилируется,
но её значение возвращается в UI: это физическая частота передатчика с точки зрения
данного прохода, и расхождение между проходами диагностично.

**Именно это делает ненужным ручной шаг `m` из гайда.**

Приорный блок, 8 членов:

```
r_prior[j] = p_j                                                   j = 0..6
r_u        = ((argp + M) − (argp_seed + M_seed)) / σ_u
```

Последний член разрешает вырождение `argp`/`M` при `e ≈ 0`: по отдельности они
свободны, а их сумма зажата. Без него фит гоняет оба параметра хаотично.

Полная длина вектора — `N + 8`.

### 4.3 Априорные σ по умолчанию (LEO)

| Элемент | σ | Обоснование |
|---|---|---|
| наклонение | 0.05° | задано запуском; доплер с одной станции его почти не определяет |
| RAAN | 0.5° | определяется геометрией прохода |
| эксцентриситет | 0.001 | орбиты околокруговые; большее — обычно патология фита |
| argp | 20° | по отдельности бессмыслен при `e≈0` |
| M | 20° | то же |
| **argp + M** | **5°** | **реально определяемая комбинация** |
| среднее движение | 0.005 об/сут | ≈1.8°/сут дрейфа вдоль трассы |
| B* | 1e-4 | практически свободен |

Это калибровочные ручки. Они передаются в запросе и **сохраняются в `od_fit_runs`**,
иначе опубликованное TLE невоспроизводимо.

Смысл конструкции: один и тот же код работает и на одном проходе, и на десяти.
На одном проходе данные двигают только момент TCA, остальное удерживает приор;
на десяти данные перевешивают приор, и элементы уезжают свободно. Никаких галочек
заморозки и никаких правил «сколько параметров размораживать».

### 4.4 Оптимизация

```python
least_squares(resid, x0=np.zeros(7), method="trf",
              loss="soft_l1", f_scale=0.5,          # кГц
              x_scale=1.0, xtol=1e-10, ftol=1e-10, gtol=1e-10,
```

### 4.5 RMS и отчёт

Как в `compute_rms` (`rffit.c:1704`) — по данным, невзвешенно, в кГц:

```
rms   = sqrt(Σ_i (f_i − fac_i·F_k)² / N)
rms_k = то же по одному наблюдению
```

Возвращаются **и до-фитовый, и после-фитовый** RMS, чтобы было видно, помог ли фит.

Дополнительно фит сообщает, какие направления оказались **зажаты приором**
(сравнение `|Δa_j|/σ_j` с единицей). Это позволяет UI написать «эксцентриситет
не сдвинулся — данные его не определяют» вместо показа числа, которое на самом деле
просто затравка.

Невязки возвращаются плоским массивом `{observation_id, point_index, mjd,
residual_khz, model_hz}`. Пара `(observation_id, point_index)` — **единственный
идентификатор точки** во всех трёх панелях UI.

## 5. Перенос эпохи

Порт `rv2el` из sattools (`propagate.c`):

```python
def reepoch(seed, target_mjd):
    r, v = sgp4_at(seed, target_mjd)        # TEME, км и км/с
    orb0 = classel(r, v, target_mjd)        # оскулирующие
    orb  = orb0
    for _ in range(4):                      # неподвижная точка
        r1, v1 = sgp4_at(orb, target_mjd)
        orb1   = classel(r1, v1, target_mjd)
        orb    = wrap_angles(orb + orb0 - orb1)
    orb.bstar, orb.cospar = seed.bstar, seed.cospar
    orb.ndot = orb.nddot = 0.0
    orb.epoch = target_mjd
    return orb
```

`classel` — извлечение кеплеровых элементов из положения и скорости,
`mu = 398600.5 км³/с²` (WGS72, как в sgp4), `n = 86400/(2π)·sqrt(mu/a³)`.

**Обёртка углов в [0,360) после каждого сложения обязательна**, иначе неподвижная
точка расходится вблизи 0/360.

### Формирование строк TLE

Основной путь — `sgp4.exporter.export_tle`: он уже делает 69 символов,
контрольные суммы и alpha-5.

Проверить round-trip на всех `.tle` из `strf/`. Если не сойдётся — откат на
`format_tle` из `rffit.c:111` дословно, с построением `sbstar` тем же перетасовыванием
цифр и контрольной суммой `(Σ цифр + количество минусов) mod 10`.

**`assert len(line) == 69` перед возвратом.** Django валидирует ровно 69 символов,
иначе ошибка длины всплывёт только в момент публикации.

Alpha-5 нужен для номеров ≥ 100000. Синтетические номера СОНИКС (70000–100000)
остаются пятизначными, но обработать надо всё равно — это два вызова библиотеки.

## 6. Идентификация

Две ступени, потому что полный фит каждого кандидата дороже скрининга примерно
в сто раз.

**Ступень 1 — скрининг без фита.** Для каждого кандидата: одна векторная прогонка
SGP4 по точкам трека, профилирование несущей в замкнутом виде, RMS. Элементы
не двигаются. Порядка 1.5 млн вычислений SGP4 на наблюдение при полном каталоге —
секунды векторизованным `sgp4`.

Порядок перебора: сначала объекты того же запуска по INTDES (обычно этого хватает),
при неудаче — весь активный каталог.

**Ступень 2 — честный фит топ-20** по результатам скрининга, с приорами на элементы
каждого кандидата.

Результат — список кандидатов с RMS в очередь на подтверждение человеком.
Правильный объект обычно даёт RMS на порядок меньше остальных.
